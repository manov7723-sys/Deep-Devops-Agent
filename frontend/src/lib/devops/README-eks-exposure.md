# EKS public exposure — ALB by default, never NLB

**Status:** active decision · **Adopted:** 2026-07 · **Applies to:** every generated
Kubernetes Service/Ingress and every EKS cluster this codebase builds.

Read this before changing anything in `deploy-manifest.ts`, `eks.ts`, or the
`lbType_*` wizard questions in `agent/agent.ts`.

---

## The incident

Every frontend Service we generated looked like this:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: ai-agentic-app-frontend
  labels:
    app.kubernetes.io/managed-by: deepagent
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: external
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
spec:
  type: LoadBalancer
```

Those annotations ask AWS for a **Network Load Balancer**. Three things went wrong
at once:

1. **Our AWS account cannot create NLBs.** AWS returns `OperationNotPermitted`.
   ALB creation *is* permitted.
2. **Kubernetes surfaces that failure as nothing.** The Service sits at
   `EXTERNAL-IP <pending>` indefinitely. `kubectl get svc` shows no error, the
   pods are healthy, the logs are clean. It reads as "the LB is still
   provisioning" — for hours.
3. **NLB is the wrong layer anyway.** It is L4. A plain HTTP frontend wants L7:
   path/host routing, WAF, native ACM TLS termination. All ALB-only.

Two follow-on problems surfaced during the fix:

4. **The AWS Load Balancer Controller was not in any IaC.** It had been installed
   by hand with `eksctl create iamserviceaccount` + `helm install`. That does not
   survive a cluster rebuild and no teammate could reproduce it.
5. **The IAM policy was stale.** The manually-attached
   `AWSLoadBalancerControllerIAMPolicy` predated
   `elasticloadbalancing:DescribeListenerAttributes`, so ALB provisioning failed
   with `403 AccessDenied` *even after* we switched to Ingress/ALB.

## The decisions

### 1. Default exposure is ClusterIP + Ingress (ALB)

Generated by `buildDeployManifest()` in [`deploy-manifest.ts`](./deploy-manifest.ts):

```yaml
apiVersion: v1
kind: Service
spec:
  type: ClusterIP          # ← not LoadBalancer
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    kubernetes.io/ingress.class: alb            # deprecated but still honored
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb                          # modern form
```

Both the annotation and `ingressClassName` are emitted so the ALB is claimed
regardless of which controller version the cluster runs.

`host` is **optional**. Without one the Ingress is a catch-all rule and the user
gets the ALB's own DNS name — no domain purchase needed to have a working URL.

### 2. NLB is opt-in only

`exposeMode: "nlb"` still exists for genuine L4/TCP workloads (gRPC streaming,
raw sockets). It is never auto-selected, and the wizard labels it
*"NOT available on this AWS account"*.

The legacy `useAwsNlb` boolean no longer forces NLB annotations. It was a second,
silent path to the same outage; it survives in the type only so previously stored
specs still parse.

### 3. The controller is Terraform-managed

[`eks.ts`](./eks.ts) emits, for every cluster it builds:

- `enable_irsa = true` on the EKS module
- `module "lb_controller_irsa"` — the IRSA role, trust scoped to
  `kube-system:aws-load-balancer-controller`
- `kubernetes_service_account.aws_lb_controller` — pre-created and annotated
  (the chart runs with `serviceAccount.create=false`)
- `helm_release.aws_lb_controller` — the chart itself
- Subnet tags on **both** VPC paths: a new VPC gets them from the VPC module;
  a reused VPC gets `aws_ec2_tag` resources that detect public vs private from
  each subnet's `map_public_ip_on_launch` and tag accordingly

One `terraform apply`. Nothing manual. Survives a rebuild.

### 4. The IAM policy is fetched upstream, not taken from the module

We deliberately do **not** use:

```hcl
attach_load_balancer_controller_policy = true   # ← DO NOT
```

That flag attaches a policy **snapshot vendored inside terraform-aws-modules/iam**,
which goes stale as the controller adds permissions in new releases. It is exactly
how we shipped a role missing `DescribeListenerAttributes`.

Instead:

```hcl
data "http" "alb_controller_policy" {
  url = ".../aws-load-balancer-controller/${local.alb_policy_ref}/docs/install/iam_policy.json"
}

resource "aws_iam_policy" "alb_controller" {
  policy = data.http.alb_controller_policy.response_body
}
```

**The two version locals must stay in sync:**

```hcl
alb_chart_version = "1.8.1"   # Helm chart  → helm_release
alb_policy_ref    = "v2.8.1"  # controller tag → IAM policy
```

Chart `1.8.x` ships controller `v2.8.x`. Bumping one without the other risks a
controller that needs a permission its policy does not grant — the same 403 class
of failure. **Bump them together.**

> **Why a pinned tag and not `main`?** Both are always-current in the sense that
> matters. The tag additionally makes a re-apply of an old commit reproducible and
> guarantees the policy matches the controller actually running. Tracking `main`
> means an upstream edit can appear as an unexplained diff in an unrelated PR.
> To switch, change `alb_policy_ref` to `"main"` — one string.
>
> **Air-gapped?** Replace the `data "http"` with a vendored
> `iam_policy.json` + `file("${path.module}/iam_policy.json")` and add a calendar
> reminder to refresh it on controller upgrades.

## How a mode is chosen at deploy time

`deploy_my_app` resolves `exposeMode` in this order:

1. **The user's answer** to the wizard's `lbType_<service>` question always wins.
2. A `host` was supplied → `ingress` (nginx).
3. Otherwise auto-detect:
   | Controller running? | Node subnets | → mode | why |
   |---|---|---|---|
   | yes | any | `alb` | the standard path |
   | no | all public | `classic` | in-tree Classic ELB needs no controller |
   | no | any private | `alb` + loud warning | a Classic ELB *cannot* attach to private subnets; emitting one would recreate the `<pending>` hang. Emit the correct manifest and tell the operator to install the controller. |

Controller presence is a real check (`kubectl get deploy -n kube-system
aws-load-balancer-controller`), not an assumption — see `detectAlbController()`
in [`../cloud/aws-onboard.ts`](../cloud/aws-onboard.ts).

The chosen mode and the evidence behind it are recorded in the deploy's
`cdNotes`, so a stuck deploy can be diagnosed from the run output alone.

## Do not

- ❌ Make `type: LoadBalancer` the default again for HTTP services.
- ❌ Add `aws-load-balancer-nlb-target-type` outside the `exposeMode === "nlb"` branch.
- ❌ Reintroduce a boolean that flips NLB on implicitly.
- ❌ Switch back to `attach_load_balancer_controller_policy = true`.
- ❌ Bump `alb_chart_version` without bumping `alb_policy_ref`.
- ❌ Install the controller by hand on a cluster this codebase manages.

## Symptom → cause quick reference

| Symptom | Likely cause |
|---|---|
| `EXTERNAL-IP <pending>` forever, no events | NLB requested on an account without NLB permission, **or** subnets missing `kubernetes.io/role/elb=1` |
| Ingress created, no ALB appears | AWS Load Balancer Controller not installed |
| ALB starts then `403 AccessDenied` in controller logs | Stale IAM policy — check `alb_policy_ref` matches `alb_chart_version` |
| `OperationNotPermitted` in events | Account cannot create that LB type — use ALB |
