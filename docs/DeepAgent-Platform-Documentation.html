01 Overview

What the platform does, and the one architectural decision everything else follows from.

DeepAgent turns a conversation into running infrastructure. A user describes what they want — a Kubernetes cluster, an application deployed, a database connected — and the agent executes it: generating Terraform, provisioning through cloud APIs, building container images, applying manifests, and wiring credentials.

The self-contained principle

Every cloud operation runs server-side using stored credentials and REST APIs. The platform never asks a user to install a CLI, run aws configure, execute az login, or paste a kubeconfig. This constraint shapes the entire codebase — where a typical runbook would say "run this command," the platform has a tool that performs the equivalent API call.

The practical consequence: the product works identically from a laptop, a phone, or a headless environment, and a user with no DevOps background can complete flows that normally require a terminal.

03 Agent & tool layer

148 registered tools, cloud-gated so the agent is only ever offered capabilities the connected provider actually supports.

Tools are typed functions with JSON Schema inputs. Each declares its own preconditions and returns structured output the agent reasons over. A registry maps cloud-specific tools to their provider, so an Azure-connected project never sees grant_eks_access and an AWS project never sees attach_acr_to_aks.

04 MCP connectors

The platform ships an MCP connector registry with credential management. It is a catalogue and credential vault — not, today, the agent's execution path.

Accuracy note

The agent does not currently invoke MCP servers at runtime. No MCP SDK is installed, and there is no client transport or tool-invocation code. Agent capabilities come from the native tool layer described in §3.

What exists is the surrounding infrastructure: connector records, per-connector OAuth, encrypted credentials, per-project attachment, and an admin console to manage them. This is the groundwork for MCP execution, not MCP execution itself.

What the registry models

ModelPurpose
McpConnector A registered MCP server — name, description, auth type, health status, and observed call-volume and latency figures.
McpOAuth Platform-level OAuth for a connector: encrypted access and refresh token references, granted scopes, issuer, expiry.
McpCredential Non-OAuth secrets — API keys, personal access tokens, role ARNs. Stored as encrypted references, never plaintext.
ProjectMcpConnection Attaches a connector to a project, allowing per-project authorization separate from the platform-level grant.

Path to execution

Making MCP live requires an MCP client SDK, a transport (stdio or SSE), a tool-discovery step that merges remote tools into the agent's registry, and a policy for how remote tools inherit the existing cloud gating and approval rules. The data model already accommodates all of it.

06 Core flows

The four operations that make up a full delivery cycle, and what the platform does at each step without user intervention.

A · Cluster provisioning

A wizard collects cluster shape; the platform validates every answer against the subscription's live capabilities before generating a line of Terraform.

01
Live capability check
Kubernetes versions, VM SKUs, availability zones and disk types are fetched per region and filtered to what the account can actually provision — so the picker cannot offer a combination the apply would reject.
02
State backend
The user reuses an existing remote state store or the platform creates one — storage account or bucket plus container — verified to exist before terraform init runs.
03
Generate & apply
Terraform is written to the repository and executed as init → plan → apply, with per-stage logs streamed to the pipeline view. Production applies queue for approval.
04
Server-side correction
Values the account cannot support are substituted before apply — an unsupported zone, an unavailable SKU, an oversized ephemeral disk — and every substitution is reported rather than applied silently.

B · Application deployment

01
Repository analysis
Detects the stack and whether the repository is a monorepo, returning one deployable service per application with its build context and port.
02
Single form
Namespace, registry per service, external exposure, load-balancer type, packaging, auto-deploy and push-vs-GitOps — collected in one submission, not a sequence of questions.
03
Artifact generation
Dockerfiles, Kubernetes manifests or a Helm chart, and exactly two workflow files — ci.yml and cd.yml — with services expressed as a build matrix rather than duplicated per service.
04
Access provisioning
Registry push credentials, cluster RBAC for the deploying identity, and image-pull permission for the cluster's node identity are all granted before the first pipeline run.
05
Build, deploy, verify
CI builds and scans every image in parallel; CD applies manifests, waits on rollout, and rolls back automatically if the health check fails.

C · Database connection

One action makes an existing managed database usable by a deployed application. The network step differs per cloud because each cloud's access model differs.

01
Establish access
AWS adds a security-group rule referencing the cluster's node groups. Azure resolves the cluster's egress addresses and adds firewall rules for them. GCP grants an IAM identity through Workload Identity and injects the Cloud SQL Auth Proxy — no IP rule to maintain or leave stale.
02
Write the secret
A Kubernetes Secret carrying DATABASE_URL plus discrete DB_* keys, with the TLS mode each provider requires.
03
Wire and roll
The Secret is injected into every Deployment via envFrom and pods are rolled — because pods read Secret values only at container start, and a Secret nothing consumes is invisible to the application.
04
Create and migrate
Optionally creates the database, then runs migrations inside the pod that actually holds the schema, waiting for the rollout to complete first so migrations target the new configuration rather than the previous one.

D · Application configuration

Signing keys and third-party credentials are pasted once in .env form, written as a Secret, wired into every Deployment, and the pods rolled. Values pointing at localhost are detected and reported — a local callback URL in a cluster surfaces only as an opaque OAuth nonce error.

07 Self-healing

Failure classes the platform diagnoses and repairs without user intervention. This is the substance of the "agentic" claim.

Pipeline failures are classified by inspecting job logs. Each recognised class maps to a repair tool the agent calls itself; the playbook explicitly forbids telling the user to perform these steps manually.

SymptomRoot causeAutomated repair
Registry login fails Registry credentials missing or rotated repair_azure_acr_push_auth
kubectl cannot authenticate Cluster credential stale, empty, or pointing at a deleted cluster repair_cd_kubeconfig
Forbidden on every kubectl call Deploy identity has no cluster RBAC role grant_aks_access
ImagePullBackOff Cluster node identity lacks pull permission on the registry attach_acr_to_aks
Role lacks cluster describe Pipeline role predates a permission grant setup_github_oidc_ecr
Cannot impersonate service account Workload Identity binding missing or not propagated repair_gcp_wif_binding
Credential expired mid-session Short-lived token past its lifetime Re-issued inline, request retried
Migration blocked by extension Provider blocks the database extension the schema requires Extension allow-listed before migrating
Rollout fails health check New revision unhealthy Automatic rollback to the previous revision
Design principle

An exit code of zero is not treated as proof of success. Several of these classes were originally invisible because a command printed usage text and exited cleanly, or a step reported "done" having done nothing. Operations that matter now assert on their output — a migration must say it applied migrations, not merely fail to error.

08 Reporting

A daily operational digest per namespace, combining cluster state with Prometheus metrics.

Applications are discovered across every connected cluster by their management label, so AWS, Azure and GCP need no separate discovery paths — the stored kubeconfig abstracts the provider. Results are grouped by namespace, which is the unit users recognise and the natural boundary for who should receive which report.

SourceReported
KubernetesReplica health, ready count, restart totals, container images, last rollout
PrometheusCPU cores, working-set memory, request rate, error rate, p95 latency
  • Recipients per namespace — many addresses, individually pausable without deletion.
  • Delivered daily at 10:00 local time, on the existing scheduler tick.
  • Once-per-day guarantee enforced in the database, so a process restart cannot re-send.
  • Metrics are optional — a cluster without monitoring still receives a health report, with the omission explained.
  • Send now executes the identical code path as the scheduled job, so testing it proves the schedule.

10 Current limitations

Stated plainly, because a document that omits them is not useful for planning.

AreaStatus
MCP executionRegistry and credential management only; the agent does not invoke MCP servers at runtime.
Database provisioningImplemented for AWS RDS. Azure and GCP support connecting an existing instance but not creating one.
TLS for deployed appsApplications are exposed over HTTP. HTTPS requires an ingress controller with certificate management, or a CDN in front.
Terraform executionRuns on the application host. Long applies are sensitive to network interruption; a hosted runner would remove this.
Application secretsProvided by the user. Cryptographic keys could be generated automatically, leaving only third-party credentials to supply.
Cost visibilityEstimation and snapshots exist; continuous per-resource attribution does not.
